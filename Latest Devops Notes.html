1. Introduction to DevOps

1.1 What is DevOps? (Explained Like You're Brand New)

Imagine a restaurant. There are two teams:

  • The chefs — they create new dishes (this is the Development team).
  • The waiters — they deliver food to customers (this is the Operations team).

In the old days, chefs and waiters barely talked. The chef would finish a dish and say "It's ready!" — but the waiter wouldn't know how to serve it, or the plate would be cold by the time it reached the customer. Customers got angry.

DevOps is what happens when the chefs and waiters sit together, share recipes, build a system where food reaches the customer hot and fast, and constantly get feedback from customers to improve the menu.

📌 The formal definition: DevOps is a culture, a set of practices, and a collection of tools that bring software developers and IT operations together so software can be built, tested, and released quickly, reliably, and continuously.
📖 Real Story — Why DevOps Was Invented

In 2009, a company called Flickr was deploying new code to production 10 times per day. Their competitors were doing it once every few months. How? They had merged their development and operations teams. At a conference, two Flickr engineers gave a talk called "10+ Deploys Per Day: Dev and Ops Cooperation at Flickr" — and the DevOps movement was born.

Today, companies like Amazon deploy code every 11.7 seconds on average. Netflix deploys thousands of times per day. That is only possible because of DevOps.

This is why Amazon can deploy code thousands of times per day — no team is waiting for another team's approval. That's DevOps culture in action.

2. Linux Fundamentals for DevOps

2.1 Why Every DevOps Engineer Must Learn Linux

Imagine being a mechanic who doesn't know what an engine is. That's a DevOps engineer without Linux skills.

Here's the truth: 99% of the servers you'll work with run Linux. Every Docker container runs Linux. Every AWS EC2 machine you spin up is Linux by default. Kubernetes nodes? Linux. CI/CD runners? Linux.

📖 Real Story — Why Linux Won

In the 2000s, most companies ran Windows Server or Unix (like Solaris). But Linux was free, open-source, and could run on cheap hardware. Google built its entire search engine on Linux. Amazon built AWS on Linux. When the cloud era arrived, Linux was ready and Windows wasn't. Today, Linux powers 96% of the world's top 1 million web servers.

2.2 The Linux Terminal — Your New Best Friend

Instead of clicking icons, in Linux you type commands. This sounds scary at first, but it's actually more powerful — you can automate anything.

2.3 Shell Scripting — Automating Repetitive Work

A shell script is just a text file with a list of commands. You run it once, and it does everything. This is the foundation of automation.

📖 Real Story — Why Scripting Saves Careers

At a company I worked with, a junior engineer used to spend 3 hours every Friday manually checking if all 40 servers were healthy. We wrote a 20-line script. Now it runs every 10 minutes, checks all 40 servers, and emails the team only if something is broken. That junior engineer got promoted within 6 months because they automated themselves out of boring work.

Example 1: Health Check Script

#!/bin/bash
# health-check.sh — Check if our application is responding

set -e   # "exit immediately if any command fails" — makes scripts safer

APP_URL="http://localhost:8080/health"
MAX_RETRIES=5
RETRY_DELAY=10

echo "🔍 Checking if $APP_URL is alive..."

for i in $(seq 1 $MAX_RETRIES); do
    # curl fetches the URL. The %{http_code} extracts just the status code.
    HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" "$APP_URL")

    if [ "$HTTP_CODE" -eq 200 ]; then
        echo "✅ App is healthy (attempt $i)"
        exit 0    # success — exit with code 0
    fi

    echo "⚠️  Attempt $i failed (HTTP $HTTP_CODE). Retrying in ${RETRY_DELAY}s..."
    sleep $RETRY_DELAY
done

echo "❌ App did not become healthy after $MAX_RETRIES attempts"
exit 1   # failure — exit with non-zero code

Example 2: Log Rotation Script

#!/bin/bash
# rotate-logs.sh — Compress logs older than 7 days to save disk space

LOG_DIR="/var/log/myapp"
ARCHIVE_DIR="/var/log/archives"
DAYS_OLD=7

mkdir -p "$ARCHIVE_DIR"

# find any .log file older than 7 days, then compress it
find "$LOG_DIR" -name "*.log" -mtime +$DAYS_OLD | while read logfile; do
    filename=$(basename "$logfile")
    timestamp=$(date +%Y%m%d_%H%M%S)

    gzip -c "$logfile" > "$ARCHIVE_DIR/${filename}.${timestamp}.gz"
    rm "$logfile"

    echo "Archived: $logfile"
done

# Delete archives older than 30 days
find "$ARCHIVE_DIR" -name "*.gz" -mtime +30 -delete

3. Version Control with Git

3.1 What is Git? (In Plain English)

Imagine you're writing a book. Every time you finish a chapter, you save a copy: Chapter1_v1.docx, Chapter1_v2.docx, Chapter1_v2_final.docx, Chapter1_v2_final_EDIT.docx… it gets messy fast.

Git solves this. It's like Google Docs' "version history" — but for code, and much more powerful. It remembers every change you ever made, who made it, and why.

📌 Key terms:
  • Repository (repo): A folder that Git is tracking. Contains all versions of all files.
  • Commit: A snapshot of your work. Like saving a game.
  • Branch: A parallel universe where you can try new things without breaking the main version.
  • Merge: Combining your branch back into the main version.
  • Remote: A copy of the repo on a server (like GitHub), so teammates can share.

📖 Why the Staging Area Exists (Real Answer)

Imagine you edited 10 files but only 3 of them are related to the "add login button" feature. The staging area lets you say "I want to commit only these 3 files with a message about the login button." The other 7 files stay uncommitted, waiting for their own commit. This is why Git is so powerful — you can craft clean, meaningful commits.

3.3 Essential Git Commands (With Explanations)

# ========== SETUP (do once per machine) ==========
git config --global user.name "Your Name"
git config --global user.email "your.email@example.com"

# ========== STARTING A REPO ==========
git init                                # Turn current folder into a Git repo
git clone https://github.com/user/repo.git   # Download an existing repo

# ========== DAILY WORKFLOW ==========
git status                              # What's changed?
git add app.js config/                  # Stage specific files
git add .                               # Stage everything

git commit -m "feat: add login button"  # Save a snapshot with a message

git log --oneline --graph --all         # See history as a graph

git push origin main                    # Send commits to remote

# ========== BRANCHES ==========
git checkout -b feature/login           # Create branch AND switch to it
git switch main                         # Switch back to main (newer syntax)

git merge feature/login                 # Merge login branch into main

git branch -d feature/login             # Delete merged branch
git push origin --delete feature/login  # Delete the remote copy too
💡 Commit message convention (industry standard):
  • feat: — a new feature (e.g., feat: add payment gateway)
  • fix: — a bug fix (e.g., fix: cart total rounding error)
  • docs: — documentation change
  • refactor: — code cleanup, no behavior change
  • test: — adding tests

4. Cloud Computing Fundamentals

4.1 What is Cloud Computing? (Analogy First)

You need electricity for your home. Two options:

  1. Buy a generator, buy fuel, maintain it, fix it when it breaks — this is owning your own servers ("on-premises").
  2. Plug into the electricity grid and pay for what you use — this is cloud computing.

Cloud computing means renting computing power (servers, storage, databases) from a provider, over the internet, and paying only for what you use.

📌 Formal definition: Cloud computing is the on-demand delivery of IT resources (compute, storage, databases, networking, software) over the internet with pay-as-you-go pricing.
📖 Real Story — Netflix and AWS

Netflix has 260+ million subscribers and streams billions of hours of video every month. In 2008, Netflix's own data center had a major database corruption incident that stopped DVD shipments for 3 days. That's when they decided to move everything to AWS.

Today, Netflix runs entirely on AWS — but here's the clever part: they don't own a single server. During peak hours (evening), they rent thousands of servers. At 3 AM when everyone's asleep, they shut most of them down. Their monthly bill fluctuates by millions of dollars, but they only pay for what they use.

📖 Real Story — Why Multi-AZ Matters

In 2011, a major AWS outage in the us-east-1 region brought down Reddit, Quora, Foursquare, and Hootsuite for hours. Why? Because they had deployed everything in a single Availability Zone. When that AZ lost power, so did they.

Smart companies now deploy across at least 3 AZs. If one fails, the other two keep serving users. This is called High Availability (HA). It costs slightly more, but it saves you from 3 AM emergency calls.

5. Networking in the Cloud

5.1 What is a VPC? (The Office Building Analogy)

Think of a VPC as an office building for your cloud resources.

  • The building has its own address (the CIDR block, like 10.0.0.0/16).
  • Inside, there are floors called subnets.
  • Some floors are public — anyone can walk in from the street (internet-accessible).
  • Some floors are private — only people already inside can access them (databases, internal apps).
  • There's a front door called the Internet Gateway that connects your building to the internet.
  • There's a reception desk called a NAT Gateway that lets private-floor workers go out to the internet (but outsiders can't come in).

📖 Real Story — Why VPCs Save Companies

A startup once put their database in a public subnet with an open firewall rule. A hacker found it within 4 hours using automated scanners and downloaded 2 million customer records. The fine was $4 million. If the database had been in a private subnet, the hacker would never have even been able to reach it. VPC design is not optional — it's survival.

If a hacker finds a bug in your web server, they only compromise the web tier. They can't directly touch the database because it's in a separate private subnet with its own security group. 6. Compute Services

6.1 What is Compute? (The Analogy)

Compute = the "brain" of your application. It's the CPU and RAM that run your code.

In the cloud, you rent compute in different sizes, like renting an apartment:

  • Studio (t3.micro) — small, cheap, good for a personal website or dev environment.
  • 2-bedroom (m6i.large) — general purpose, good for most apps.
  • Penthouse (r6i.4xlarge) — huge memory, for in-memory databases.
  • Home gym (g4dn.xlarge) — has a GPU, for AI/ML workloads.

6.3 Launching an EC2 Instance

# Step 1: Find the latest Amazon Linux 2 image ID
# (AMIs are "disk images" — like a template for a fresh server)
AMI_ID=$(aws ssm get-parameters \
    --names /aws/service/ami-amazon-linux-latest/amzn2-ami-hvm-x86_64-gp2 \
    --query 'Parameters[0].Value' \
    --output text)

# Step 2: Create a key pair (like a physical key to SSH into the server)
aws ec2 create-key-pair \
    --key-name myapp-key \
    --query 'KeyMaterial' \
    --output text > myapp-key.pem
chmod 400 myapp-key.pem   # protect the key file — only you can read it

# Step 3: Launch the instance
aws ec2 run-instances \
    --image-id $AMI_ID \
    --instance-type t3.micro \
    --key-name myapp-key \
    --security-group-ids sg-12345678 \
    --subnet-id subnet-12345678 \
    --user-data file://user-data.sh \
    --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=web-server-1}]'

10. Infrastructure as Code (Terraform)

10.1 What is Infrastructure as Code? (The Recipe Analogy)

Imagine building a house two ways:

  1. Manually — you tell a construction worker "put a wall there, put a window there." If you need to rebuild it, you have to describe everything again, hoping they remember.
  2. With blueprints — you hand them detailed architectural drawings. Anyone can rebuild the same house from scratch, perfectly.

Terraform is the blueprint for cloud infrastructure. You write text files describing what you want. Terraform builds it.

📖 Real Story — Rebuilding an Entire Company in 30 Minutes

A startup I know had their entire AWS infrastructure defined in Terraform. One day, a junior engineer accidentally deleted the wrong VPC and destroyed production. Panic. But the senior engineer said: "Just run terraform apply." 30 minutes later, the entire infrastructure — 50+ EC2 instances, 5 RDS databases, load balancers, security groups — was rebuilt identically. Zero data loss (databases had backups). Without IaC, this would have taken 3 days.

10.5 Terraform State — The Most Important Concept

Terraform keeps a file called terraform.tfstate. It's a map of what Terraform thinks exists in the cloud.

⚠️ Critical rules:
  • Never commit .tfstate to Git. It contains secrets.
  • Store it remotely (S3, Azure Blob) so the team shares one state.
  • Enable state locking (DynamoDB) so two people can't apply simultaneously.
# backend.tf — Store state in S3 with locking
terraform {
  backend "s3" {
    bucket         = "myapp-terraform-state"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

13. Containerization with Docker

13.1 What is Docker? (The Shipping Container Analogy)

Before shipping containers, loading a cargo ship was chaos. Barrels, boxes, sacks — every port had to handle each item differently. Someone invented the standardized steel container, and suddenly any crane, any ship, any truck could handle any container. Shipping exploded in efficiency.

Docker containers are the shipping containers of software. A container packages your app + its dependencies (libraries, runtime, configs) into one sealed unit. It runs the same on your laptop, on a colleague's machine, in the cloud. No more "but it works on my machine!"

📖 Real Story — The "Works on My Machine" Problem

Picture this: a developer's Node.js app runs perfectly on their Mac (Node 20.10). They deploy to a Linux server (Node 14.2). It crashes because Node 14 doesn't support a feature they used. Hours of debugging. Docker solves this by bundling the exact runtime version inside the container. Whatever machine runs the container runs it identically.

13.4 A Real Dockerfile

# Multi-stage build — smaller final image
# Stage 1: Build the app
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Production image (only what's needed to run)
FROM node:20-alpine AS production
WORKDIR /app
RUN addgroup -g 1001 -S nodejs && adduser -S nextjs -u 1001   # non-root user for security
COPY package*.json ./
RUN npm ci --only=production
COPY --from=builder --chown=nextjs:nodejs /app/dist ./dist
USER nextjs
EXPOSE 3000
HEALTHCHECK --interval=30s CMD wget --spider http://localhost:3000/health || exit 1
CMD ["node", "dist/server.js"]
💡 Why multi-stage? The builder stage can be 1GB (with all dev tools). The final image is only ~150MB (just what's needed to run). Smaller images pull faster, deploy faster, and have less surface area for attackers.

17. Serverless Computing

17.1 What is Serverless? (The Taxi Analogy)

Owning a car = paying for insurance, parking, gas, maintenance — even when you don't drive. Taking a taxi = paying only when you ride. Serverless is the taxi of compute.

You write a function. You upload it. It only runs when triggered. You pay only for the milliseconds it runs. No servers to manage, no idle costs.

📌 Despite the name: there ARE servers — you just don't manage them. AWS does. That's the "server-less" part: serverless from your perspective.

17.2 AWS Lambda — Real Example

# lambda_function.py — Resize images automatically
import boto3
import os
from PIL import Image

s3 = boto3.client('s3')

def handler(event, context):
    """
    Triggered automatically when a file is uploaded to S3.
    Downloads the image, creates a thumbnail, uploads the thumbnail.
    """
    for record in event['Records']:
        source_bucket = record['s3']['bucket']['name']
        source_key = record['s3']['object']['key']

        # Download original
        s3.download_file(source_bucket, source_key, '/tmp/original.jpg')

        # Resize to thumbnail
        img = Image.open('/tmp/original.jpg')
        img.thumbnail((200, 200))
        img.save('/tmp/thumbnail.jpg')

        # Upload thumbnail to a different bucket
        s3.upload_file('/tmp/thumbnail.jpg', 'myapp-thumbnails', source_key)

    return {'statusCode': 200}

Instead of developers throwing code over a wall to ops, they collaborate. We use automation (CI/CD), infrastructure as code (Terraform), and containers (Docker) so that we can deploy many times per day without breaking things. The goal is to shorten the time from "idea" to "in customers' hands" while maintaining quality.

Q2: What is the difference between Continuous Delivery and Continuous Deployment?

Sample answer:

Both ensure every change that passes tests is ready to deploy. The difference is the last step:

  • Continuous Delivery: The artifact is ready, but a human clicks "deploy" to production. Common in regulated industries.
  • Continuous Deployment: Fully automated — code goes to production the moment tests pass. This is what Amazon/Netflix do.

Q3: You pushed code and CI failed. What do you do?

Sample answer:

  1. Read the CI logs to see exactly which stage failed (lint, test, build).
  2. Try to reproduce locally — run the same command.
  3. Check the diff — what did I change? Often it's a typo or an import.
  4. If it's a flaky test, re-run once to confirm.
  5. Fix, commit, push — the pipeline re-runs automatically.
  6. If it's a deeper issue, I'll add logging or debug output and re-run.

Section B: Cloud & Networking

Q4: What is the Shared Responsibility Model?

Sample answer:

In cloud computing, security is split:

  • The cloud provider (AWS/Azure/GCP) is responsible for security of the cloud — physical data centers, hardware, networking, hypervisor.
  • You (the customer) are responsible for security in the cloud — your data, access control (IAM), encryption, patching your OS, and configuring firewalls correctly.

A common misconception is "the cloud is secure by default." It isn't — you must configure it correctly.

Q5: What is a VPC and how do you secure it?

Sample answer:

A VPC is an isolated network inside the cloud — my own private section where I deploy resources. I secure it by:

  • Placing databases and internal services in private subnets (no internet access).
  • Using Security Groups (stateful firewalls at the instance level) to allow only necessary ports.
  • Using Network ACLs (stateless firewalls at the subnet level) for an extra layer.
  • Routing internet traffic through a NAT Gateway for outbound only from private subnets.
  • Enabling VPC Flow Logs to audit all network traffic.

Section C: IaC & Configuration Management

Q6: Terraform vs Ansible — when do you use which?

Sample answer:

They solve different problems:

  • Terraform is for provisioning infrastructure — creating servers, VPCs, databases. It keeps state and knows what exists.
  • Ansible is for configuring what's inside those servers — installing packages, deploying app code, setting up cron jobs.

In practice, I use both together: Terraform provisions the servers, Ansible configures them.

Q7: Where do you store Terraform state in a team?

Sample answer:

Always in a remote backend — never on a laptop. Typically S3 (with encryption enabled and versioning on) and a DynamoDB table for state locking, so two engineers can't apply at the same time. The state file contains secrets and is sensitive, so it's never committed to Git.

Section D: Containers & Kubernetes

Q8: A pod is stuck in Pending state. How do you debug?

Sample answer:

First, kubectl describe pod <name> — the Events section tells you exactly why. Common causes:

  • Insufficient resources: no node has enough CPU/memory. Fix: add nodes or reduce requests.
  • Node selector / taints: pod requires a node it can't be scheduled on.
  • PVC not bound: the pod is waiting for storage.
  • Image pull error: usually shows in Events as ErrImagePull.

Q9: Difference between ClusterIP, NodePort, LoadBalancer?

Sample answer:

  • ClusterIP (default): Only reachable inside the cluster. Used for service-to-service communication.
  • NodePort: Exposes the service on every node's IP at a high port (30000–32767). Used for dev/testing.
  • LoadBalancer: Provisions a real cloud load balancer (AWS ALB/NLB, Azure LB). Used for public-facing apps in production.

Section E: Scenario-Based (The Real Test)

Q10: Production is down. Walk me through your response.

Sample answer (structure matters):

  1. Restore service first, investigate later. If I can roll back in 30 seconds, I do that before debugging.
  2. Check monitoring dashboards — Grafana, CloudWatch. When did things start failing? What changed?
  3. Check recent deployments — 90% of the time the cause is a recent change.
  4. Look at logs and traces — identify the failing component.
  5. Communicate — update the status page and notify stakeholders.
  6. Fix the root cause — after service is restored, dig into why it happened.
  7. Write a post-mortem — blameless. What can we change so this can't happen again?

Q11: How would you reduce our AWS bill by 30%?

Sample answer:

  1. Right-size instances — many VMs are 20% utilized. Downsize them.
  2. Enable Auto Scaling — turn off servers when traffic drops (nights, weekends).
  3. Use Spot Instances for fault-tolerant workloads — up to 90% cheaper.
  4. Buy Reserved Instances / Savings Plans for predictable workloads — 30–70% off.
  5. S3 lifecycle policies — move old data to Glacier automatically.
  6. Delete unused resources — idle load balancers, orphaned EBS volumes, unused Elastic IPs.
  7. Tag everything — you can't optimize what you don't measure.

Q12: Design a highly-available web application on AWS.

Sample answer:

I'd design it across three Availability Zones for redundancy:

  • Route 53 for DNS with health checks.
  • Application Load Balancer across 3 public subnets (one per AZ).
  • Auto Scaling Group of web servers in private subnets, minimum 2 instances per AZ.
  • RDS Aurora in Multi-AZ mode — one primary, one standby for automatic failover.
  • ElastiCache (Redis) for session state — so any server can serve any user.
  • S3 + CloudFront for static assets — cheap, fast, global.
  • CloudWatch alarms → SNS for on-call notifications.
  • AWS WAF in front of the ALB for DDoS / SQLi protection.

The result: if any single AZ fails, the other two keep serving traffic with no user-visible impact.
